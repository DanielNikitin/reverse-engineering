# Техническое задание

## Проект: Распределённое отказоустойчивое KV-хранилище с консенсусом Raft (mini-etcd)

**Срок:** 7 дней
**Целевая аудитория исполнителя:** Senior-разработчик с опытом распределённых систем + AI-ассистент (Claude Code)

---

## 1. Цель проекта

Разработать распределённое key-value хранилище, обеспечивающее:
- **Строгую консистентность** (linearizability) для операций чтения и записи;
- **Отказоустойчивость**: система продолжает работать при отказе меньшинства узлов (для кластера из N узлов — до `(N-1)/2` отказов);
- **Автоматическое восстановление лидерства** без вмешательства человека;
- Демонстрируемую корректность через воспроизводимые chaos-тесты (сетевые партиции, задержки, падения узлов).

**Явно вне scope (сознательное ограничение под недельный срок):**
- Membership changes (динамическое добавление/удаление узлов кластера "на лету", joint consensus) — фиксированный состав кластера, заданный при старте.
- Log compaction / snapshotting — допускается неограниченный рост лога в рамках демо.
- Персистентность на диск с fsync-гарантиями — допускается in-memory storage с упрощённым WAL без строгих durability-гарантий при полном отключении питания.
- Балансировка нагрузки клиентских запросов между узлами — клиент сам находит текущего лидера (retry-логика).
- TLS/mTLS между узлами — сеть считается доверенной (внутренний кластер).

## 2. Функциональные требования

### 2.1. Консенсус-протокол (Raft)

| ID | Требование |
|---|---|
| FR-1 | Реализовать leader election согласно алгоритму Raft: randomized election timeout (диапазон 150–300 мс), RequestVote RPC, голосование с учётом up-to-date лога кандидата |
| FR-2 | Реализовать log replication: AppendEntries RPC, commit index, применение записей к state machine только после репликации на большинство узлов |
| FR-3 | Гарантировать **election safety**: в рамках одного term не может существовать двух узлов, считающих себя лидером |
| FR-4 | Гарантировать **log matching property**: если два лога содержат запись с одинаковым index и term, все предыдущие записи в этих логах идентичны |
| FR-5 | Реализовать корректный **step-down**: узел, получивший RPC (RequestVote или AppendEntries) с term больше своего текущего, немедленно переходит в состояние follower и обновляет свой term |
| FR-6 | Реализовать heartbeat-механизм: лидер периодически (раз в 50 мс) отправляет пустые AppendEntries для поддержания лидерства и предотвращения новых выборов |

### 2.2. Линеаризуемые операции чтения/записи (Read Index)

| ID | Требование |
|---|---|
| FR-7 | Операции записи (`PUT`, `DELETE`) применяются к state machine только после коммита в лог большинством узлов |
| FR-8 | Операции чтения (`GET`) реализуются через **read index protocol**: перед ответом на запрос лидер обязан подтвердить своё лидерство через heartbeat-раунд с большинством узлов (защита от stale read при устаревшем лидере, ещё не узнавшем о своём смещении) |
| FR-9 | Запрос на узел, не являющийся лидером, должен возвращать редирект/ошибку с указанием текущего известного лидера (или `NO_LEADER`, если лидер неизвестен) |

### 2.3. Клиентский API

| ID | Требование |
|---|---|
| FR-10 | HTTP/gRPC API с операциями: `PUT /kv/{key}`, `GET /kv/{key}`, `DELETE /kv/{key}` |
| FR-11 | Клиентская библиотека с автоматическим обнаружением текущего лидера и retry при смене лидера (exponential backoff, максимум 5 попыток) |
| FR-12 | Идемпотентность записи: повторная отправка одного и того же запроса (например, при таймауте и retry) не должна приводить к двойному применению операции (client request ID + дедупликация на стороне лидера) |

### 2.4. Инфраструктура тестирования (обязательная часть, не опциональная)

| ID | Требование |
|---|---|
| FR-13 | Симулятор сети (network simulator) на уровне транспортного слоя, позволяющий программно инъецировать: полную потерю пакетов между парой узлов, асимметричную партицию (A видит B, но B не видит A), задержки (jitter 0–500 мс), временное "подвешивание" узла (process pause) |
| FR-14 | Набор chaos-сценариев как воспроизводимые тесты (см. раздел 4) |
| FR-15 | Логирование каждого узла с обязательными полями: `node_id`, `current_term`, `role (leader/follower/candidate)`, `commit_index`, `last_applied` — в структурированном формате (JSON), пригодном для последующего скрипта-анализатора |
| FR-16 | Скрипт-инвариант-чекер: после каждого chaos-теста автоматически парсит логи всех узлов и проверяет отсутствие нарушений election safety и log matching property (см. раздел 5) |

## 3. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-1 | Кластер из 5 узлов должен продолжать корректно работать при отказе любых 2 узлов одновременно |
| NFR-2 | Время восстановления лидерства после отказа текущего лидера — не более 1 секунды (при стандартных таймаутах) |
| NFR-3 | Пропускная способность записи (single-threaded client) — не менее 500 operations/sec на локальном кластере (loopback network) |
| NFR-4 | Все узлы реализованы как независимые процессы (не потоки в рамках одного процесса) — обязательное условие для реалистичности сетевого партиционирования |
| NFR-5 | Код разбит на модули с чёткими интерфейсами: `Transport`, `Storage`, `StateMachine`, `ConsensusModule` — каждый модуль тестируется изолированно (unit-level) |

## 4. Обязательные chaos-сценарии для приёмки

Каждый сценарий должен быть воспроизводимым тестом (не ручной проверкой) и включён в CI:

1. **Symmetric partition**: кластер из 5 узлов делится на группы 2+3. Проверить: группа меньшинства (2) не выбирает лидера; группа большинства (3) выбирает лидера и продолжает принимать записи; после снятия партиции меньшинство синхронизирует лог без потери данных.
2. **Leader isolation (asymmetric partition)**: текущий лидер теряет связь со всеми, но сам продолжает считать себя лидером. Проверить: клиент, обращающийся к изолированному "лидеру" на чтение через read index, либо блокируется, либо получает явную ошибку — **не должен вернуть stale-данные**.
3. **Rolling restart**: последовательный перезапуск каждого узла кластера по одному с паузой 2 сек между перезапусками. Проверить: ни на каком этапе не теряются закоммиченные записи.
4. **Simultaneous candidate race**: искусственно сбросить election timeout у 3+ узлов одновременно (спровоцировать split vote). Проверить: система сходится к единственному лидеру в течение разумного числа раундов выборов (не более 5 попыток), split-vote не приводит к дедлоку.
5. **Network delay injection**: ввести задержку 200–400 мс между всеми узлами. Проверить: система не начинает ложные перевыборы (election timeout должен быть откалиброван с запасом относительно инъецированной задержки), запись/чтение продолжают работать, хоть и медленнее.
6. **Term comparison edge case**: узел получает AppendEntries с term, равным его текущему term, но от узла, который сам не является легитимным лидером (искусственно смоделировать через тестовый мок). Проверить: узел корректно игнорирует некорректный запрос, не переключает свой vote/leader tracking ошибочно.

## 5. Критерии приёмки (definition of done)

Проект считается выполненным, если:

- [ ] Все функциональные требования FR-1 – FR-16 реализованы и покрыты тестами
- [ ] Все 6 chaos-сценариев из раздела 4 проходят автоматически и воспроизводимо (минимум 20 прогонов подряд без нарушения инвариантов — из-за рандомизации таймаутов баги могут проявляться не в каждом прогоне)
- [ ] Скрипт-инвариант-чекер (FR-16) не находит ни одного нарушения election safety и log matching property во всех прогонах
- [ ] Проведён явный тест на stale read (сценарий 2) — задокументировано, что БЕЗ read index protocol тест проваливается, а С ним — проходит (демонстрация того, что защита реально работает, а не просто присутствует в коде)
- [ ] Нагрузочный тест подтверждает NFR-2 (recovery time) и NFR-3 (throughput) с зафиксированными числами в отчёте
- [ ] Документация содержит: диаграмму состояний узла (follower/candidate/leader), описание read index protocol с обоснованием, почему наивное чтение с лидера небезопасно, и лог одного полного прогона chaos-сценария №2 с комментарием, что именно в логе доказывает корректность

## 7. Технологический стек (рекомендуемый, не строгий)

- **Язык:** Go (богатая экосистема для сетевого кода, встроенная поддержка горутин для симуляции узлов как отдельных процессов через `os/exec` или отдельные бинарники) или Rust (сильные гарантии на уровне типов для конкурентности)
- **RPC:** gRPC или простой JSON-over-HTTP для наглядности логов
- **Логирование:** структурированное (`zerolog`/`zap` для Go), обязательно с полями из FR-15
- **Тестирование chaos:** собственный network simulator на уровне абстракции `Transport` (не требует реальной сетевой изоляции через Docker/iptables — для целей демо достаточно программной инъекции на уровне интерфейса)

## 8. Явно определённые риски проекта

| Риск | Митигация |
|---|---|
| Баги в consensus-логике не воспроизводятся детерминированно | Прогон каждого chaos-сценария минимум 20 раз в CI, а не один раз |
| Read index protocol реализован некорректно, но тесты по умолчанию его не ловят | Обязателен явный сценарий 2 с зафиксированным "было плохо без protocol → стало хорошо с ним" |
| Scope creep (желание добавить snapshotting/membership changes) | Жёстко зафиксирован scope в разделе 1; при избытке времени — в backlog, не в v1 |
